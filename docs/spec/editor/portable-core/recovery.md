# Saving and outside writers

The text-first editor keeps no recovery log: edits live in memory and reach disk only as a markdown write. A crash loses at most the unsaved window below. Nothing creates a `.futo-editor-recovery` directory (maintainer decision, 2026-11-02).

- Opening a note reads its exact disk bytes (`NOTE_NOT_FOUND` if absent) and sets the saved baseline to them; there is no replay, recovery issue or pending checkpoint at open, and opening an unchanged note writes nothing. A host that already showed a note's first screens from a `read_for_editor` read opens on that read (otherwise on the file); if the file changed since, that read stays the saved baseline and the first save is due at once, so the outside write is merged or parked as below. → crates/futo-notes-store/src/editor_session/mod.rs, crates/futo-notes-store/src/editor_session/quick_open.rs
- Every input method applies its edit in memory only and schedules a save; the engine's accept hook stays so the portable page can capture each edit for its host request. → crates/futo-notes-store/src/editor_session/save.rs
- The markdown file is saved 500 ms after the last edit, and at most 2 s after the first unsaved edit while typing continues, on an injected clock. The store reports the remaining delay (none when clean, zero once due) and saves when due. → crates/futo-notes-store/src/editor_session/save.rs, crates/futo-notes-store/src/editor_session/clock.rs
- Checkpoint means "write the markdown now": identical source and baseline converge with no write when disk is unchanged or missing; native clean attachments reconcile an existing outside source through the same history-preserving adoption as dirty drafts, while portable automatic saves leave page-owned source untouched. Otherwise it runs the persist-or-park decision (write, merge, recreate or park a conflict copy) under the store gate and vault mutation guard and returns the existing flush disposition and complete mutation. On success the baseline becomes the saved source and the save deadlines clear. → crates/futo-notes-store/src/editor_session/checkpoint.rs, crates/futo-notes-store/src/flush.rs
- When checkpoint parks the draft, the attachment retargets to the parked note and acquires its lease; if that fails the error is returned. → crates/futo-notes-store/src/editor_session/checkpoint.rs
- A failed save reports the error and does not pause input; the draft stays in memory and the next save attempt is scheduled 2 s later so a host loop does not spin. → crates/futo-notes-store/src/editor_session/save.rs, crates/futo-notes-store/src/editor_session/checkpoint.rs
- Closing (and native detach) saves first, then releases the lease; if the save fails the session stays attached so the caller can retry or copy the draft. Dropping a session without closing loses unsaved edits, like a crash. → crates/futo-notes-store/src/editor_session/facade.rs
- One process can attach only one session to a note, including through different store handles, and legacy whole-note saves of an attached note are refused. Independent app processes editing the same vault remain unsupported, as for the existing local note engine. → crates/futo-notes-store/src/editor_session/lease.rs
- Rename, move and relink while attached are in memory: the attachment follows the note to its collision-resolved destination, refusing if another session is attached there, and an unsaved draft is kept and later saved under the new id. A failed preparation leaves the session on its old id. → crates/futo-notes-store/src/editor_session/identity.rs
- A successful own-action backlink rewrite adopts source only when the live source still equals its pre-action disk source, no composition is active and the session is not portable; otherwise it keeps the exact draft, selection and history, and either way the saved baseline becomes the rewritten bytes. Portable sessions keep the relink offer. → crates/futo-notes-store/src/editor_session/identity.rs
- An adopted relink is one command: the session replaces its changed byte window with the store's exact rewritten bytes, as one accepted edit and one Undo step whose Undo restores the prior link text. Existing Undo entries are never rewritten: history is a stack, so an older entry applies only after that Undo has restored the exact source it was recorded against; like any new edit, the relink clears Redo. Selection keeps unchanged bytes and leaves replaced text at its replacement's start (the edits are the characters that differ). Identity-only, failed and skipped rewrites leave source and both stacks verbatim; a composition in progress is `CompositionActive`. → crates/futo-notes-editor/src/engine/commands/wikilinks/relink.rs, crates/futo-notes-editor/tests/fixtures/engine/wikilinks.json, crates/futo-notes-store/tests/editor_lifecycle/relinks.rs
- The baseline-aware draft rename/move workflows follow a matching attachment to its authoritative final identity, including a parked draft at the requested destination; a stale peer source and its backlinks remain untouched. → crates/futo-notes-store/src/editor_draft.rs, crates/futo-notes-store/src/editor_session/checkpoint.rs
- Deleting an attached note removes the file under the store gate; on success the attachment is terminal, its draft is discarded and later input, checkpoints and cached portable requests report `SessionDeleted`. A failed delete leaves the attachment untouched. Folder deletion keeps its move-notes-up policy. → crates/futo-notes-store/src/notes.rs, crates/futo-notes-store/src/folders.rs
- An outside write to a native attached note (sync adoption, another tool) needs no hook: the next save compares saved base, current disk source and draft under the store gate and vault mutation guard; clean three-way merges commit both independent contributions, including changes to different Unicode words within one paragraph at the same id and return the authoritative source, flush result and complete mutation. Ambiguous overlap retains the dated conflict-copy fallback and leaves the outside version untouched. Legacy `flush_draft` and portable automatic saves retain parking until their renderer opts into authoritative adoption. → crates/futo-notes-store/src/flush.rs, crates/futo-notes-store/src/editor_session/checkpoint.rs
- Finer-grained merging uses Unicode word boundaries without normalizing source bytes; competing edits to one word, different insertions at the same position and delete/edit overlap preserve both versions through the conflict-copy fallback. Conservative boundary ambiguity may also park a draft. → crates/futo-notes-merge/src/lib.rs, crates/futo-notes-store/src/tests/flush_draft.rs
- Native merge adoption prepares the selection (with its caret pin and carried formats) and both local history stacks before the disk write: each retained Undo and Redo step's text is merged with the outside contribution, and each step must stand on bytes both texts keep and turn one rebased text into the next exactly; Undo and Redo retain outside contributions and restore the selection each step recorded, moved with the outside change. Failed persistence leaves source, history and saved baseline available for retry. An ambiguous historical step, or an outside change that touches, opens or closes front matter, conservatively parks both versions instead of clearing history. → crates/futo-notes-editor/src/engine/external.rs, crates/futo-notes-editor/src/session/external.rs
- Applying an adoption checks that the session, revision and selection are the ones it was prepared against (`StaleClaim` or `StaleRevision` otherwise, changing nothing), refuses during composition, and replaces only the changed window of the note as one edit that is read again from the lines it touches, never a reopen; it returns an ordinary view change. A merged source equal to the current text changes nothing and keeps both stacks. → crates/futo-notes-editor/src/engine/external.rs
- A clean native session whose history cannot be rebased (size bounds, ambiguity, front matter) follows the outside source with both stacks dropped, as if reopened; outside bytes may rewrite front matter there, local input never may. Its selection still moves with the change. → crates/futo-notes-store/src/editor_session/checkpoint.rs, crates/futo-notes-editor/src/engine/external.rs
- Ordinary checkpoints preserve provisional composition. When actual outside divergence requires adoption, native checkpoint settles marked text first and reports its coordinated view change, then attempts merge; consumers drain coordinated changes on failures as well as success. → crates/futo-notes-store/src/editor_session/checkpoint.rs
- Merge adoption bounds historical reconstruction: current/merged bytes plus retained patch bytes must be at most 1 MiB, and that estimate multiplied by retained entry count (at least one) must be at most 16 MiB. Exceeding either bound preserves both complete versions through parking without removing local history; note and history sizes themselves remain unrestricted. → crates/futo-notes-editor/src/engine/external.rs
- Explicit portable/WASM `adopt_merged_source` validates the flush revision, refuses active composition, rebases local history and returns a normal Append request carrying the changed window; a merged source equal to the page's own text has no Append to send and is refused (`UnrepresentableFormat`). The worker never silently advances page-owned source/history during automatic saving. → crates/futo-notes-editor/src/portable.rs, crates/futo-notes-editor/src/wasm.rs
- Saving is the host worker's job (a timer calling the store's save-if-due and checkpoint), never a page request; the portable page only appends edits and resumes. → crates/futo-notes-store/src/editor_session/mod.rs

- Nonempty authored note writes end with a line ending. Saving appends one when absent, using CRLF for an existing CRLF note and LF otherwise; existing terminal blank lines remain unchanged. The in-memory engine keeps exact draft bytes, and baselines, merges and own-action relinks account for this serialization rule. Opening an unchanged note still writes nothing. A draft that differs from its baseline is written unless the disk already holds its exact bytes or exactly the bytes saving it writes, so a line ending typed at the end of a note that had none is saved. → crates/futo-notes-store/src/notes.rs `saved_note_source` `disk_holds`, crates/futo-notes-store/src/editor_session/checkpoint.rs, crates/futo-notes-store/src/tests/editor_session/saving.rs
