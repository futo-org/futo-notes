# Find in note

These are the portable replacement core's contracts. The shipping Milkdown find
bar keeps [its contract](../find-in-note.md) until renderer integration and cutover;
platform bars stay thin and render the engine's report verbatim.

- Matching is case-insensitive literal search over the visible display text, so hidden Markdown markers and link destinations are not findable while text spanning a hidden mark (`**bo**ld`) matches. Every Greek sigma is one letter; a character whose lowercase is longer matches only itself. Occurrences never overlap. → crates/futo-notes-editor/src/session/find.rs, crates/futo-notes-editor/tests/find.rs
- A line break inside one paragraph (including quote and list-item continuation lines) reads as one space; a match never crosses a block boundary (blank line, list item, quote or heading edge) or a fenced-code line. A match inside a table stays within one cell's content: pipes, padding, delimiter rows and row breaks are barriers (the scan request carries them as `barriers`). → crates/futo-notes-editor/src/inline/find.rs, crates/futo-notes-editor/src/session/blocks/tables.rs, crates/futo-notes-editor/tests/find.rs
- Opening or changing the query scans once, as an explicit find action, and makes the first match at or after the selection start current. Stepping moves to the next or previous match with wrap, selects it and returns a reveal request; during composition it is a no-op, as selection changes are. Zero matches and a closed find make stepping a no-op; closing clears matches, keeps the query for the next open and leaves the selection. The report carries one-based current, total, the current display range and its tight source range. State lives on the note's session only. → crates/futo-notes-editor/src/session/find.rs
- Find never edits source, accepts an edit or adds an Undo step; stepping changes only the selection. → crates/futo-notes-editor/tests/find.rs
- Input only logs its display window (O(1)); matches are mapped through that log on the next read, matches inside a replaced window are dropped, and the report is `stale` until a rescan lands. A host takes a scan snapshot after input settles, scans it on any thread and applies the result; a result for another session, revision or query generation (including after close) is rejected with no state change. Past 64 unread edits the matches are dropped until a rescan lands instead of retaining unmappable ranges. `FindWork` proves ordinary input adds no scan. → crates/futo-notes-editor/tests/find.rs
- The same operations are exposed unchanged through the portable session, WASM, Store and native FFI (`find_set_query`, `find_step`, `find_close`, `find_report`, `find_matches`, `find_scan_request`, `find_apply_scan`, pure `find_scan`); portable session and WASM also have `*_utf16` variants of range-taking calls (`find_matches`, the table calls); native FFI has no such twins, so hosts convert UTF-16 ranges with `utf16_to_display` first. Portable input awaiting host acknowledgement rejects find queries as busy; closing always succeeds. → crates/futo-notes-editor/tests/find/wasm-find-consumer.mjs, crates/futo-notes-ffi/tests/editor_find.rs
- *(Android native text-first editor, dev builds only)* A match inside a table cell reveals the grid and focuses that cell's native field; highlights are not drawn on the text inside the open cell field. The rest of find on the native text-first editor is shared with iOS ([mobile/find.md](../mobile/find.md)). Verified on the emulator 2026-11-03 (five matches including cell matches; source byte-identical). → `TextFirstFindTest`; evidence `spec-318-artifacts/333/` (`find-highlights.png`, `find-cell-field.png`)
