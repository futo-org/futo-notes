# Long notes

- *(mobile)* A note longer than 16 KB first shows the screens parsed from its first 16 KB alone (quick open), read-only, while the whole open runs. The cut is the start of a top-level block at column 0 after an empty line, with that block's line inside the bytes read and the block after the cut parsed but not shown: the chunk rule of [performance.md](../performance.md), applied to the Rust engine. Quick open declines (the note opens whole, as before) for a leading U+FEFF, front matter that does not close inside the read, any shown `[` when a `]:` appears anywhere after the cut (definitions resolve document-wide), and from a lone CR on; the engine's rows must also end at the cut. The first screens it shows are the whole open's byte for byte and style for style (compared as bytes, not as Unicode equivalents), so the handover keeps the view's text, styles, scroll and caret and appends the rest after them; should they ever differ, the whole open replaces them as before. → crates/futo-notes-editor/src/quick_open.rs, crates/futo-notes-editor/src/host/quick_plan.rs, crates/futo-notes-store/src/editor_session/quick_open.rs, apps/ios/Sources/Editor/TextFirst/TextFirstEditorController+Opening.swift, apps/ios/Tests/Editor/TextFirst/TextFirstOpeningTests.swift, apps/android/app/src/main/java/com/futo/notes/textfirst/EditorEngineStorage.kt
- *(mobile)* Until the whole open lands, scrolling and reading work, a tap places the caret (the keyboard reads it at once; the session takes it on landing, mapped through any edits before it), and typed keys, Enter and Backspace wait in order and are applied once after it, never early and never dropped. Toolbar edit buttons are disabled meanwhile, and nothing is written until the session exists. Leaving before it lands still applies what was typed, then saves it. → crates/futo-notes-editor/src/host/pending_edits.rs, apps/ios/Sources/Editor/TextFirst/TextFirstEditorController+Opening.swift, apps/android/app/src/main/java/com/futo/notes/textfirst/EditorEngineOpening.kt
- *(mobile)* Select All selects the complete canonical note at once, however long; Copy, Cut, typing over it, toolbar commands and saves use the complete canonical source. A view that cannot highlight a selection that long shows the highlight around the viewport and moves it as the note scrolls. → apps/ios/Sources/Editor/TextFirst/TextFirstEditorController+SelectAll.swift, apps/ios/Tests/Editor/TextFirst/TextFirstOpeningTests.swift
- *(mobile)* Toolbar taps made while an earlier toolbar action is running are dropped, and leaving checkpoints the accepted draft. A toolbar action over a selection too large to finish within a frame (Select All, then Bold on a note of megabytes) runs off the main thread, so the note stays scrollable; its result is applied at once for the text on screen and the rest of the restyle follows in slices, between which touches and scrolling are served. → apps/ios/Sources/Editor/TextFirst/TextFirstEditorController+Commands.swift, apps/ios/Tests/Editor/TextFirst/TextFirstOpeningTests.swift, apps/android/app/src/main/java/com/futo/notes/textfirst/ToolbarCommandGate.kt
- *(iOS)* Keys typed while such a toolbar action runs are not applied. → TextFirstEditorController+Input.swift
- *(mobile)* While a finger is on the note, or the text menu (Cut, Copy, Select All) is open, background restyling waits and resumes when neither remains. → apps/ios/Sources/Editor/TextFirst/TextFirstEditorController+Style.swift, apps/android/app/src/main/java/com/futo/notes/textfirst/TextFirstRenderHold.kt
- *(mobile)* Find over a note of 200,000 characters or more scans on the engine's worker, not the main thread; only the latest query is scanned when several arrive meanwhile. → apps/ios/Sources/Editor/TextFirst/TextFirstFind.swift
- *(mobile)* A new width (rotation, split view) keeps the reader's line at the top; the caret, selection and unsaved edits are untouched. → apps/ios/Tests/Editor/TextFirst/TextFirstLongNoteTests.swift
  > **Gap:** *(iOS)* at the bottom of a note of megabytes a new width holds the main thread for seconds (2.1 s for a 2.3 MB note on the simulator): TextKit 2 lays the note out again from its first line. Android bounds the view to a prefix and streams the rest; a TextKit 2 text view has no such cut.
- *(mobile)* Closing keeps the rendered view until its screen lets go, then releases the large display text and the closed engine's buffers. → apps/ios/Tests/Editor/TextFirst/TextFirstOpeningTests.swift, apps/android/app/src/main/java/com/futo/notes/textfirst/TextFirstEditTextRelease.kt
- *(iOS)* Measured 2026-11-06 on the iOS 27.2 simulator (Debug app, release Rust, a 390x700 window; `TextFirstLongBenchTests`, one run each, about 15% noise), for the 1,302,835-byte, 20,007-line long test note and a 2,292,240-byte, 230,000-line note of `## Section i` / `Body line i with **bold**.` blocks. Open to first text 94 / 249 ms before, 42 / 39 ms after (quick open); open to editable 94 / 249 ms before, 94 / 266 ms after; full styling 0.3 / 1.1 s before, 1.2 / 2.5 s after (paced slices). Keystroke p95 near the top 2.3 / 4.5 ms before, 2.8 / 4.7 ms after, near the bottom 1.8 / 4.9 ms before, 1.9 / 4.3 ms after. Select All then Bold held the main thread 1.4 / 5.5 s before (plus 2.2 s to highlight the selection of the larger note); after, the tap returns at once and the longest main-thread stall is 84 / 570 ms, the engine finishing in 1.3 / 3.9 s. A new width held the main thread 0.8 / 2.1 s (unchanged). → apps/ios/Tests/Editor/TextFirst/TextFirstLongBenchTests.swift
