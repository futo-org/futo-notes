# Clipboard and system text actions

- *(mobile)* System text actions other than the clipboard (Look Up, Translate and other process-text apps, Share, smart text classification, the keyboard's view of the selection) receive the selection's visible display text without Markdown markers; Copy and Cut alone export Markdown. The view holds display text only, and only the clipboard actions, undo and redo are routed to the engine. Verified on iOS by a unit test; Android is code-verified. → apps/android/app/src/main/java/com/futo/notes/textfirst/TextFirstClipboard.kt, apps/android/app/src/main/java/com/futo/notes/textfirst/DisplayMirror.kt, apps/ios/Sources/Editor/TextFirst/TextFirstTextView.swift, apps/ios/Tests/Editor/TextFirst/TextFirstEditorTests.swift `systemTextActionsSeeDisplayTextWhileCopyAndCutExportMarkdown`
- *(Android)* Cut removes the selection only after the system clipboard accepted the copied Markdown. A selection the clipboard refuses (over Android's ~1 MB transaction limit, e.g. Select all in an 80,000-block note) leaves the note and the clipboard unchanged and shows the long toast `editor.android.clipboardTooLarge`; Copy refuses the same way. Verified live on a Pixel 7a 2026-11-06 (2,377,853-char select-all cut: note kept all 160,001 lines, toast shown, no crash). → apps/android/app/src/main/java/com/futo/notes/textfirst/TextFirstClipboard.kt, apps/android/app/src/main/java/com/futo/notes/textfirst/EditorEngine.kt, `TextFirstStreamingCommandsTest.cutTooLargeForTheClipboardKeepsTheNoteAndReportsIt`
- *(Android)* A selection that covers a note's front matter (Select all, or the start handle carried to the top) tints its card as it tints any selected row, so what Copy takes is drawn as selected. The card is one, behind every line of the front matter, in the note and in a block drag's preview. → apps/android/app/src/main/java/com/futo/notes/textfirst/MetadataCard.kt `drawMetadataCard`, apps/android/app/src/androidTest/java/com/futo/notes/textfirst/TextFirstMetadataSelectionTest.kt
- *(Android)* A hold on a word with the keyboard up selects that word, with handles and the text menu, whatever selection stood before: a range an Undo restored, or a word left selected after Bold, ends at the hold and is never brought back by it. A hold inside a standing selection keeps it and lifts nothing: with its menu open the menu stays, and no text is dragged (the note neither starts a text drag nor takes a drop, which the editor cannot make as one move); a long click with no touch (an accessibility service's) does not end it either. → apps/android/app/src/main/java/com/futo/notes/textfirst/HoldSelectsWord.kt `endSelectionUnderHold`, apps/android/app/src/androidTest/java/com/futo/notes/textfirst/TextFirstHoldSelectsWordTest.kt
