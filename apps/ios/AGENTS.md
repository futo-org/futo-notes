# AGENTS.md — Native iOS App

Native SwiftUI app on the shared Rust core (`futo-notes-ffi`) with an embedded web editor. This is
the **shipping** iOS app — there is no Tauri mobile shell. See @README.md for structure and
root AGENTS.md for cross-layer rules.

The Xcode project is generated by `xcodegen` from `project.yml`, and `Sources/Generated/` holds the
UniFFI Swift bindings. Both are generated — edit `project.yml` or the FFI crate, never the output.

## Building and running

| Goal | Command |
| --- | --- |
| Booted simulator | `just ios-native` |
| Connected iPhone, Debug (`com.futo.notes.dev`) | `just ios-native-device` |
| Connected iPhone, Release (prod `com.futo.notes`) | `just deploy-ios` |
| Compile-only sanity | `just build-ios-native` |
| Swift Testing suite | `just test-ios-native` |

After **any** change to `futo-notes-ffi` or a crate it re-exports, run `just build-rust-ios` before
building — otherwise you are testing old bindings, and the symptom looks like "my change did
nothing" or a Swift compile error on a missing symbol. The `just *-native` recipes do this for you;
a direct `xcodebuild` does not.

`just build-ios-native` passes `EXCLUDED_ARCHS=x86_64` because `build-rust-ios.sh` assembles an
arm64-only simulator slice. `just test-ios-native` instead targets one concrete simulator by id, so
it links without that flag.

## Constraints

- **CRITICAL — dev/prod data split.** Debug builds use bundle id `com.futo.notes.dev` and the
  `~/Documents/fake-notes` root, gated by `#if FUTO_DEBUG_BUILD`. Release uses `com.futo.notes` and
  `~/Documents/futo-notes`. Never weaken this; a debug build must never touch real notes.
- **Push testable logic down into the Rust crates rather than Swift.** Swift should orbit the FFI
  facade, not reimplement note rules — a rule that exists in both WILL drift (root AGENTS.md §12).
- **`NotesStore.swift` holds one of three independent copies of the default notes-root split**
  (Rust `vault_location.rs`, Android
  `apps/android/app/src/main/java/com/futo/notes/storage/NotesStorage.kt` are the others). Touch one,
  touch all.
- **I/O belongs on the `NoteVault` actor**, and `hasBootstrapped` distinguishes loading from empty
  so the shell renders immediately. Never await work before first render.
- **`ToolbarSpec.swift` and `TitleSpec.swift` are generated** from `packages/editor/src/toolbar.ts`
  and `filename.ts`. Edit the manifest and run `just toolbar-spec` / `just title-spec`.
- A new `futoBridge` message needs a hand-written host in `EditorWebView.swift` **and** its Android
  counterpart — the contract in `packages/editor/src/bridge.ts` is the source of truth.

## Testing and QA

Unit tests are Swift Testing in `apps/ios/Tests/`, run by `just test-ios-native` (needs a booted
simulator; honors `$SIM` from `just qa-claim ios`). `ServerUrlConformanceTests.swift` reads the full
shared `validateServerUrl` fixture — it is a lock, not a sample.

Device/simulator QA of the changed flow is required; keyboard, safe-area, and scroll changes need
the full matrix (new note, existing note, toolbar, scroll-during-IME). Drive the app with
`xcrun simctl` + `idb`; the full playbook is the `/verify` skill's `references/ios.md`.

**iOS 26 nav-bar toolbar items are invisible to the a11y tree and to idb taps** — list rows and the
FAB work. When automation reports "nothing happened", suspect the tool before the app.

`just sim-logs` streams os_log, but the app logs mostly via `print()`, which os_log does not
capture — for stdout use `xcrun simctl launch --console-pty booted com.futo.notes.dev`.
